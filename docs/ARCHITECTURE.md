# Architecture

One Next.js app, plus a small background agent beside it (`agent/`, see [AGENT.md](AGENT.md#background-work)). Server components read the database directly; server actions change it through a shared service layer; a handful of route handlers cover files, cron and unsubscribe. The REST API (`/api/v1`), the MCP server (`/api/mcp`) and the in-app agent (`/api/agent`) go through the same service layer, so the browser, integrations and agents follow the same rules and write the same history (see [API.md](API.md) and [AGENT.md](AGENT.md)).

## Layout

```
src/
  app/
    (auth)/          sign-in, setup, forgot, reset/[token], invite/[token]
    (app)/           everything behind the login: home, clients, people, organizations,
                     activities, calendar, files, billing (Stripe invoices and payments, customer mapping),
                     email (inbox, campaigns, audiences, templates),
                     messages (text conversations), chat (the team chat), settings
    api/             files (upload token, local upload, download), brand logo, cron
                     (campaigns, inbox, email-status, notifications, microsoft), the Resend and Twilio
                     webhooks, Microsoft sign-in (integrations/microsoft), the REST API
                     (v1/[...path]), MCP (mcp) and the agent (agent: chat, transcribe, voice)
    manifest.ts, icon.tsx, apple-icon.tsx   the installable app: manifest and generated icons
    developers/      the public API and MCP docs, generated from the operation list
    developers.md/   the same docs as one Markdown document (the page's "Copy as Markdown")
    unsubscribe/     the campaign unsubscribe page and RFC 8058 one-click endpoint
    share/           public file links: the page and the file, no sign-in
  actions/           server actions, one file per area ("use server")
  components/        UI, grouped by feature; ui/ holds the primitives; agent/ is the agent panel;
                     phone/ is the call panel, call buttons and the text composer
  db/                schema.ts (every table) and the connection
  emails/            React Email templates (layout, invite, reset, direct, campaign)
  lib/               server logic: auth, permissions, email (and the inbox sync), Stripe,
                     files, formatting, queries (lib/crm), record changes (lib/crm/service),
                     the REST API (lib/api), MCP (lib/mcp), the agent (lib/agent), push (lib/push),
                     Microsoft 365 (lib/microsoft), Twilio (lib/twilio), phone-number rules (lib/phone)
                     and the optional knowledge source (lib/knowledge)
  styles/theme.css   every color the app uses
```

## Data model

| Table | Holds |
| --- | --- |
| `users`, `sessions`, `auth_tokens`, `rate_limits` | Team, signed-in browsers, invite/reset links, sign-in and API throttling |
| `api_keys` | Workspace keys (full access, REST only), personal keys and connected apps (act as one teammate; REST and MCP). Only a hash is stored. Each teammate's agent has an `assistant` row too, with no usable token, so history can say "via Agent" |
| `agent_threads` | A teammate's conversations with the agent: title and messages (AI SDK UI messages, as JSON). Private to them |
| `agent_runs` | Work the agent does in the background for a teammate: who asked, how (chat, a mention in a note or the team chat, an assigned task, a bulk request, the API), the request, its status, its answer and what it cost. `chat_message_id` is the team chat message that called on it. `hide_at` is when the agent panel stops listing it. An activity it was handed points at its run (`activities.agent_run_id`) |
| `agent_skills` | Instructions saved for the agent: a teammate's own (`personal`) or shared with everyone by an admin (`workspace`), always on or read when relevant. See [AGENT.md](AGENT.md#skills) |
| `agent_schedules` | Scheduled jobs: work the agent does on a cadence as one teammate. A `workspace` row is an offer from an admin; a teammate who adds it gets their own copy (`from_id`). A run a job started points back at it (`agent_runs.schedule_id`). See [AGENT.md](AGENT.md#scheduled-jobs) |
| `email_forwards` | Email a teammate sent to the agent's address: whether it was accepted and why not, how the sender was verified, the run it started, the reply sent back, and the conversation it belongs to. Unique per sender and Message-ID among verified rows, so the same email is read once. Private to that teammate; its text is cleared after 30 days. See [AGENT.md](AGENT.md#email-forwarding) |
| `agent_drafts` | Emails and texts the agent wrote for a teammate to review and send. Private to that teammate; sending happens in the composer, never here |
| `push_subscriptions`, `notifications` | Devices that get push notifications (one per browser or installed app, each with its own alert types), and every notification sent, deduplicated by key |
| `workspace` | One row: name, currency, time zone, email brand kit. The time zone is the clock background work keeps (agendas, reminders, scheduled jobs, the agent); on screen each teammate sees times in their own browser's zone (`src/lib/time-zone.ts`) |
| `organizations`, `people`, `clients` | The records. Each has an owner, `custom` JSON for custom fields, `last_activity_at`, `archived_at` (soft delete), and an AI summary (`summary`, `summary_at`, `summary_started_at`) refreshed daily ([AGENT.md](AGENT.md#record-summaries)) |
| `client_people` | People on a client besides its contact, added by hand on its page |
| `client_organizations` | Organizations a client is also tied to besides its main one, kept when clients are merged ([DEDUPE.md](DEDUPE.md)). Their people are its people, their pages list it, and Stripe matching counts their people's emails (`src/lib/crm/client-organizations.ts`) |
| `activity_people` | Everyone else on an activity besides its own person: a meeting's other attendees, the other recipients of an email |
| `labels` | What each label means: a name (the string in a record's `tags`), a description and whether the app shows it. People, organizations and clients carry labels in `tags` |
| `pipelines`, `stages` | Each pipeline belongs to a client category. Stages carry a win probability (prospects) and a "needs attention" threshold in days |
| `stripe_customers`, `stripe_subscriptions`, `client_stripe_links` | A copy of every customer and subscription in the connected Stripe accounts, refreshed daily, and the corrections people made to the email matching (a customer linked by hand, a match that isn't theirs). See [Stripe](#stripe) |
| `stripe_activity` | Every invoice and payment in the connected Stripe accounts, for the Billing page. The daily sync copies the last year (all of history the first time an account is seen) and keeps older rows. See [Stripe](#stripe) |
| `product_descriptions` | What each Stripe product delivers, by its Stripe name (Settings → Services): shown behind an info icon wherever the product shows, and read by the agent |
| `services`, `service_plans`, `client_services` | Retired: services tracked by hand before Stripe drove them. Nothing reads or writes them except merging (which still moves a merged client's rows) and the Pipedrive import; kept so the data isn't lost until a migration drops them |
| `client_metrics` | Performance numbers logged over time per client ("Leads", "Days to fill") |
| `activities` | Notes, calls, emails, texts, meetings and tasks in one table. Links to a person, organization and/or client. An activity is archived with the record it was logged on (its client, else its person, else its organization; `src/lib/crm/activity-archive.ts`): work lists, counts, reminders, the agenda email, the calendar and the API leave it out, and restoring the record brings it back |
| `note_replies` | Replies under a note, oldest first: teammates answering each other, and the agent answering a note that called on it |
| `events` | Change history: who changed what, from what, to what, and through which API key |
| `files` | Metadata; the bytes live in private Vercel Blob (one row per stored file: `url` is unique). It's on the one record it was added on (`person_id`, `organization_id` or `client_id`; a file added to a note or email keeps its `activity_id`). `folder_id` is its folder on the Files page, `public_token` is set while it's public, `origin`/`chat_message_id` mark a team chat attachment, `description`/`content_notes` are what the model (or a teammate, `description_by`) wrote about it, and `embedding` is their pgvector for search |
| `file_links` | Records a file was attached to after it was uploaded, one per row, besides the ones it was uploaded on (`files.person_id` and the rest) |
| `file_folders` | Folders on the Files page, nested by `parent_id` |
| `chat_messages` | The team chat: one thread for everyone. Plain text, who it mentions, edited and deleted times, the key it came through (`api_key_id`: a personal key, a connected app or the teammate's agent), the message it answers (`reply_to_id`) and the background run a message that mentions the agent started (`agent_run_id`). `users.chat_read_at` is how far each teammate has read |
| `custom_fields` | Field definitions per record type. Values live on the record, keyed by a stable `key` |
| `saved_filters` | Saved filters on the People, Organizations and Clients lists: a name, the list it's for, its conditions (`all` and `any`) and whether it's shared with the team. See [Saved filters](#requests) |
| `email_templates`, `campaigns`, `audiences`, `outbound_emails` | Email. `audiences` are saved campaign filters. `outbound_emails` records every message sent, with its reply-to, attachments and Resend delivery status |
| `inbox_threads`, `inbox_messages` | A mirror of the workspace's Resend inboxes, linked to people, organizations and clients |
| `inbox_sends` | Who sent each email from the inbox page, by Resend's id, so the sync credits them however the send and the webhook race |
| `people_imports` | What each spreadsheet import created and changed, so it can be undone |
| `person_organizations` | Organizations a person is also at, besides their main one. Merging duplicates, by hand or with the script ([DEDUPE.md](DEDUPE.md)), keeps every organization they were at here. People also have `other_emails` and `other_phones`, which mail, call and text matching use |
| `external_ids` | Which record here came from which record in Pipedrive, so the [Pipedrive import](PIPEDRIVE-IMPORT.md) can run again without duplicating and be removed cleanly |
| `connected_accounts`, `synced_emails` | Each teammate's connected Microsoft 365 mailbox and calendar (tokens encrypted), and every message the mailbox sync looked at: shared, private (with its content, for that teammate alone) or kept out, why, and the screen's probability. See [MICROSOFT.md](MICROSOFT.md) |
| `phone_numbers`, `phone_number_users`, `phone_calls`, `text_messages` | The Twilio numbers the team uses and who may use each, and every call and text through them. Each call and text is also an activity on the record it matched. See [PHONE.md](PHONE.md) |
| `text_threads` | Text conversations for the Messages page: one per pair of our number and theirs, with its links and one read flag. Every text belongs to one (`text_messages.thread_id`) |

Choices worth knowing:

- **Clients are one table, in three categories.** A client is prospective, current or past. The category decides which pipelines it moves through (each pipeline has a `category`) and what its page shows: potential value and expected close for prospects; health, Stripe billing, performance and time since last contact for current clients; why they left and whether they'd come back for past clients. Moving between categories (`changeClientCategory`) records dates, the reason and a history entry; billing is Stripe's, so it doesn't change there. Deals were renamed to clients in place (migration `0001`), so ids, links and history carried over; won deals became current clients, lost ones prospects in a "Not now" stage.
- **Services are what Stripe bills for.** What a client has is the products on their running Stripe subscriptions (`clients.stripe_products`), and monthly revenue is what those bill a month after discounts (`clients.stripe_mrr`): the client page, the Clients table and board, the home page, AI summaries and the API's `mrr` all read them (see [Stripe](#stripe)). Without Stripe connected there's no revenue to show. Settings → Services lists every product the connected accounts have, with how many clients are on each, and says what each delivers (`product_descriptions`, matched by name without regard to case, `src/lib/product-rules.ts`); a product can be described before Stripe has it. The descriptions load with the app-wide data, so the info icon beside a product (`ProductTag` and `ProductInfo` in `src/components/clients/product-tag.tsx`) needs no round trip. Services used to be tracked by hand (`client_services`); that's retired, and old history entries about them still read as they did.
- **Activities are one table.** "Log a call" and "add a task" are the same gesture with different fields, and a record's timeline is one query. An open activity with a `due_at` is planned; one with `completed_at` or no `due_at` is history.
- **Notes are threads.** A reply (`note_replies`) stays under the note it answers instead of becoming another note, so a conversation is one entry on the timeline, in the Activities page and in the API (`replies` on the note). Replying bumps the note's `updated_at` (so open pages pick it up) and counts as contact on its records. `@` and a teammate's name in a note or reply sends them the "Mentioned in a note" push (`mentionedTeammates` in `src/lib/crm/mentions.ts`: the full name, or a first name nobody shares); a reply also tells the note's author and everyone who already replied. The agent's answer to a mention is a reply too, and a reply can call on it again.
- **A person's page shows their organization in full, and can create it.** The Organization card under their details lists everything on the organization's own Details card, read-only (website, phone, industry, address, owner, parent, labels, custom fields such as time zone), with Open to edit it there. A person at no organization gets a Create organization card instead, and typing a name that doesn't exist in their Organization field offers to add it; both open the New organization form (website prefilled from a work email, `workDomain`), and saving puts them at it in the same action (`createOrganization` with `linkPersonId`), written to both histories.
- **Links roll up.** Logging on a client fills in its contact and organization; logging on a person fills in their organization. The organization page is the whole story without joins across clients.
- **A client has people, not one person.** Its People card and the composer on its page offer its contact (`clients.person_id`), people added to it by hand (`client_people`) and everyone at its organizations, the main one and any kept from a merge (`clientPeople` in `src/lib/crm/records.ts`, each person once, in that order). Calls, emails and texts from the page start on the contact and can go to any of them. Changing the contact keeps the old one on the client.
- **An activity can be with several people.** `activities.person_id` is still the one it's mainly with; `activity_people` holds the rest (`personIds` on the activity input). A meeting on a client needs nobody named, and can name any number of the client's people; an email to several people records everyone on its To and Cc lines who is in the CRM. It shows on each person's timeline and counts as contact with each.
- **Messages land on people.** Mail (Resend inboxes and synced Microsoft 365 mailboxes), calls and texts are matched to a person by address or phone number (`src/lib/crm/match.ts`), else to an organization by website domain or main line, and roll up from there like anything logged by hand.
- **Decision makers are a star.** `people.decision_maker` marks the people at an organization who make or sign off on the decision; they sort first in the organization's people and are an audience filter. What the star is called is a setting (`records.keyContactLabel`).
- **Parent organizations are one level.** `organizations.is_parent` marks an organization others can be part of (a franchisor and its franchises); `parent_id` is the parent an organization is part of. Only a marked organization can be picked, and a parent has no parent of its own, so there are no chains or cycles to walk (`assertParentRules` in `src/lib/crm/service/records.ts`). "At this organization" then means the organization or one that is part of it (`inOrganizations` in `src/lib/crm/records.ts`): the People list's parent filter, a campaign audience's "Part of" filter and `GET /people?organizationId=` all use it, so a group is one choice instead of every franchise. The parents load with the app-wide data, so the picker opens with no round trip. Timelines don't roll up to the parent.
- **Labels are strings with a definition.** A record's labels are the lowercase strings in its `tags` (people, organizations, clients), so audiences, imports and the API keep working on plain names. `labels` gives a name its description and a hidden flag (Settings → Labels, admins). Anything that puts a label on a record (`ensureLabels` in `src/lib/crm/labels.ts`: the services, the bulk action, an import) gives it a definition if it has none, and Settings also lists labels in use that nobody has described. Renaming one rewrites every record, saved audience, unsent campaign and saved list filter (`rewriteLabel`). Deleting one takes it off every record, and is refused while an audience or unsent campaign filters on it, since dropping a filter would widen who it reaches. Hidden labels stay on their records and in the API; the app doesn't show or offer them. The definitions load with the app-wide data: chips explain themselves on hover and focus, and record pages pick labels from a dropdown (`src/components/records/labels.tsx`). The agent gets the definitions in its prompt, in a background run's first message and from `list_labels`.
- **An organization's labels carry to its people.** A person has a label when they or their organization has it (`effectiveTags`): the People list's label filter, a campaign audience's "Labeled" and "Not labeled" filters and `GET /people?tag=` all match that way, a person's page shows the carried ones dashed, and the API returns them as `organizationTags`. They aren't copied onto the person, so taking a label off the organization takes it off everyone. Labels don't carry from a parent organization to the organizations that are part of it, or from an organization to its clients. Adding a label to a parent organization on its page asks whether to copy it onto the organizations that are part of it (`addLabelsToChildOrganizations`), which is a one-time copy, not a link.
- **Labels are added in bulk from a selection.** The People, Organizations and Clients tables offer "Add labels" on selected rows (`addLabels` in `src/lib/crm/service/records.ts`): the picked labels are added to what each record has, and each record that changed gets a history entry.
- **Money is integer cents** (`bigint`), so sums never drift.
- **Board order uses fractional ranks** (`src/lib/rank.ts`): moving a card writes only that card.
- **Custom field keys never change.** Renaming a field keeps its data; archiving hides it without deleting values.
- **History is written by the server**, next to each change, in the same action. Nothing in the UI can forge it.
- **Files are scoped to their record, and reach a client from below.** A file is on the record it was added on, without rolling down (`uploadLinks`): added on a client (its page, or a note or email there), it's on that client only, not its contact or organization; added on a person or an organization, on them only. It can be attached to more records later (`file_links`). A client's Files card and timeline also show its contact's, its people's and its organization's files, marked "From …" (`inRecordView` in `src/lib/crm/files.ts`); nothing travels from a client down. `recordsFor` reads both kinds of link, so the Files page, the API and the dialog agree. The file dialog sets the whole list at once (`setFileRecords`), and each record that gains or loses the file gets a history entry. Merging records moves their links.
- **The Files page is four lists.** All files is every file in the CRM, with what it's on. General files are a lightweight shared drive: folders nest, a folder holds whatever is put in it, and the top level shows files on no record and not from chat. "On records" lists every file on a client, person or organization; "From chat" lists team chat attachments. Search in General looks through every folder. Files and folders move by drag and drop (onto a folder or a breadcrumb) or with Move. Deleting a folder first shows what's in it, then either moves it all to another folder or deletes it with the folder (which needs an admin when someone else uploaded a file or made a folder inside). Two folders in one place can't share a name. New folder is offered on All files too: the folder is made at the top of General files and opened.
- **Files describe themselves.** A small model reads each new file once and writes a short description and its key facts; they're embedded for search by meaning, and the agent, the API and MCP find and quote files by them. See [AGENT.md](AGENT.md#file-descriptions) and [API.md](API.md#files).
- **Files are internal or public.** Internal files open only for signed-in teammates (`/api/files/[id]`). Making one public gives it a random token and `/share/<token>` opens it for anyone, with a page that shows its name, a preview for pictures and a download; making it internal again clears the token, so links already sent stop working. See [SECURITY.md](SECURITY.md#files).
- **The team chat is one thread.** Everyone who can sign in reads and posts; viewers can't attach files (`src/lib/chat/service.ts`). Messages are plain text with web addresses and `[label](/path)` links picked out (`chatSegments` in `src/lib/chat/format.ts`; a path opens in the app); `@` and a teammate's name mentions them (the same rule as notes) and sends the "Mentioned in team chat" push and a [mention email](#phone-app-and-notifications), both linking to the message; teammates who chose "Every team chat message" hear about the rest. A message can reply to another (Reply on its toolbar), which shows a quote of what it answers. Attachments are files uploaded with `origin: "chat"` and claimed by the message they're posted with; deleting a message removes its files unless someone has since filed, attached or shared them. The sidebar counts messages since the teammate last had the chat open (including what their keys and agent posted for them), and mentions in red.
- **The chat is in the API and MCP.** `list_chat_messages` reads it (the last 30 days unless `from` / `to` say otherwise, `src/lib/chat/window.ts`), `get_chat_message` reads one and `post_chat_message` posts as the key's teammate, marked "Sam via Claude" ([API.md](API.md#team-chat)). The in-app agent and background runs have the same tools.
- **`@Agent` in the team chat hands it work.** A message a teammate typed in the chat that mentions the agent starts a background run (source `team_chat`) with the message as the request and the 15 messages before it, and the message it replies to, as quoted context ([AGENT.md](AGENT.md#background-work)). The message shows "Agent: working", then "done"; the answer is posted as a reply to it, from the teammate via the agent, and reads "Agent, for Sam". A message posted through a key, an app or the agent never calls on it.
- **Activity is shared with the team.** Notes, tasks, calls, meetings, texts and emails on a record are seen by everyone who opens it, whoever logged or is assigned them. What stays private is a teammate's own Outlook mail the sync marked private, their agent threads and their drafts.
- **Clients have product lines.** `clients.product_lines` holds which of TalentScout, CoRecruit, ThirdPool, HiringCenter and VRA a client is on; the Clients filter, the Products column, the board cards and the Products card on a client show it. Anyone who can edit sets it on any client (the API and MCP too). The Stripe sync replaces it whenever the client's running subscriptions belong to a line, matched by product name (`productFamily` and `syncedProductLines` in `src/lib/product-rules.ts`, which also hold the names that don't say their line, like Recruit365 or Contract Recruiter Services), and writes a `products_synced` history entry; with nothing running that belongs to a line, what was set by hand stays. Colors are `--product-*` tokens in `theme.css`. Notes, replies and team chat offer the agent first (with a sparkle, for teammates who can hand it work; picking it puts in `@Agent`, `agent.mentionName`) and then teammates alphabetically when you type `@` (`useMentionOptions` in `src/components/ui/mention-menu.tsx`, `mentionOptions` and `agentMentionNames` in `src/lib/crm/mentions.ts`).
- **Invites say what really happened.** Settings → Team badges a teammate who hasn't set a password by their latest unused invite link (`inviteStates` in `src/lib/crm/teammates.ts`, rule in `src/lib/invite-state.ts`): "Invite sent", "Invite expired", or "Not invited" (e.g. added by the Pipedrive import). Inviting, resending, and reactivating someone who never joined all go through `issueInvite` in `src/actions/settings.ts`, which makes the link, emails it and reports whether the email went out; if it didn't, the admin is shown the link to send themselves. Admins can copy a waiting invite's link any time ("Invite link" on the row, `inviteLink`), kept encrypted in `auth_tokens.sealed_token`.
- **Owners can change a teammate's email** (Settings → Team, `changeEmail` in `src/actions/settings.ts`). Sessions, passwords, invite and reset links, API keys, ownership and history all hang off the user id, so only the sign-in address changes and nobody is signed out. Invite and reset links mailed to the old address stop working; a waiting invite goes out again to the new one. Lookups by address (sign-in, mail forwarded to the agent, a teammate's own address on inbox threads) read the current one, so they follow the change.
- **Teammates have a page.** `/team/<id>` (`src/app/(app)/team/[id]`) shows a teammate to the rest of the team: role, email, what's assigned to them, what they logged lately and the records they own, each linking to the filtered list. Their name links there from a timeline, the team list and chat mentions; a teammate id opened as `/people/<id>` or `/users/<id>` lands there too.
- **Anything on a timeline can be deleted**, for everyone: notes, tasks, meetings, and calls, texts and emails sent or received through the CRM (a sensitive email that got through, say). Admins can delete anything; everyone else what they sent or logged themselves, plus mail copied from their own mailbox (`deleteActivity` in `src/lib/crm/service/activities.ts`). What was behind it stays as a tombstone, emptied of content, so a later sync or webhook never brings it back; the history says something was deleted, without an email's or text's subject.

## Requests

- **Pages** are server components wrapped in `<Suspense>`. With Cache Components the static shell (sidebar, headers) streams instantly and data fills in. `getDb()` calls `connection()`, so anything that touches the database is per-request by construction.
- **App-wide data** (team, pipelines, custom field definitions, workspace settings) loads once in the `(app)` layout and reaches client components through `AppProvider`, so pickers and menus open with no round trip.
- **Record changes live in `src/lib/crm/service/`.** Each function takes an `Actor` (`src/lib/crm/actor.ts`): a teammate in the browser, a teammate through their personal key, or a workspace key. It checks the actor's permission (`src/lib/permissions.ts`), validates with the shared schemas (`src/lib/crm/schemas.ts`), and writes history. Server actions wrap these and call `refresh()`; the API and MCP call them directly.
- **Roles** are one table in `src/lib/permissions.ts`: owners and admins can do everything, members work records, viewers only read. The interface hides what a role can't do; the server refuses it regardless.
- **Server actions** return `Result<T>` (`{ ok, data }` or `{ ok: false, error }`) through `run()` in `src/lib/action.ts`. Errors meant for people are `ActionError`s with a sentence that says what to do; anything else is logged and reported generically.
- **Saved filters are conditions, compiled to SQL.** The Filters menu on the People, Organizations and Clients lists (`src/components/table/saved-filters.tsx`) holds the viewer's own filters and the ones teammates shared; a filter in use is `?filter=<id>`. A filter is Pipedrive-style: every condition in "all", and at least one in "any". A condition reads a field of the record or of a record tied to it: a person's organization and clients, an organization's people and clients, a client's organization and contact (`fieldGroups` in `src/lib/crm/filter-fields.ts`, built-in fields and every custom field), so "clients whose organization is in the Eastern time zone" is one condition. `filterSql` (`src/lib/crm/filter-sql.ts`) turns it into one WHERE fragment that refers to the listed table by name and reads related records in aliased `exists` subqueries, so the list queries apply it unchanged. Each operator that rules records out is the negation of one that picks them, so against related records it means none of them ("no one at it is a decision maker"), and a person with no organization is "not Eastern" and has an empty time zone. A condition that can't be read (its field was deleted) matches nothing, and a filter id that's gone or private to someone else shows an empty list that says so: a broken filter never widens a list. Anyone who can edit records makes filters; only the maker or an admin changes or deletes a shared one, and anyone else can save a copy. The API and MCP read them (`list_filters`, `filterId`; [API.md](API.md#saved-filters)).
- **List state lives in the URL** (`?q=&owner=&sort=`), so views are shareable and survive reloads. The People and Organizations tables render their first 100 rows and the total, then load 100 more as you near the bottom (`usePagedRows`, `src/components/table/use-paged-rows.ts`). Each page picks its ids first (filter, sort, offset on the one table) and only then works out organizations, clients and next activity for those rows, so deep pages stay cheap; the total is counted once per view, not per page. View preferences that should follow a person across devices (board vs table, pipeline) are saved on `users.prefs`.

## Email

- `src/lib/email.ts` wraps Resend. Without `RESEND_API_KEY` it prints to the terminal.
- One-off emails (`src/actions/email.ts`) send from a person's or client's page as the teammate (their name in From) and are logged as an `email` activity. Reply-To is the teammate's own address unless they change it for that email. Sending from a Resend inbox skips Reply-To: replies come back to that inbox.
- From a client's page one email can go to several of its people: one message with everyone on To and Cc, so they can reply to all. To and Cc together hold 10 addresses at most (`MAX_EMAIL_RECIPIENTS`, well under Resend's 50 per line), checked in the composer and again on the server. `planRecipients` (`src/lib/email/recipients.ts`) keeps each address once, on To when it's on both lines; a blind copy to the sender doesn't count. Merge tags fill in for the first person on To. The `outbound_emails` row keeps both lines comma-separated and gets one delivery status for the whole email; a bounce or complaint flags only the addresses Resend's report names.
- **Attachments** are ordinary CRM files (`src/lib/email/attachments.ts`). The composer uploads them to the record first, so they also show in its Files; the email stores the list (`EmailAttachment[]`) and the bytes are read from Blob at send time. Up to 10 files and 20 MB per email. Templates and campaigns can carry attachments too.
- Campaigns render their HTML on every save with the current brand kit, keep merge tags as `{{tags}}`, and fill them per recipient at send time. Sending claims the campaign with one conditional `UPDATE`, sends in batches of 100 through Resend's batch endpoint with idempotency keys, records each recipient, and the cron resumes interrupted sends. A send can be retried safely at any point. Resend's batch endpoint can't carry attachments, so a campaign with files sends the same groups one email at a time (idempotency key per recipient), which is slower.
- Each campaign recipient also gets an `email` activity linked to the person, their organization and the client they matched, so campaign emails are on every timeline. They don't count as contact: `notCampaignEmail` (`src/lib/crm/activities.ts`) keeps them out of "last contacted", the Activities page and the home feed, and they don't move `last_activity_at`. Instead they set `people.last_campaign_at`, shown as "Last campaign" on the person and in the People table, and usable as an audience filter ("no campaign in the last N days"). Last contact is personal outreach only: anything logged by hand, and one-off emails from a person's, organization's or client's page.
- Reply-To for campaigns starts as the email of whoever set the campaign up, and can be changed on the campaign. A blank one falls back to the creator at send time. Duplicating a campaign keeps a shared reply-to (sales@…) but swaps the original author's own address for yours. There is no workspace-wide reply-to.
- Merge tags (`src/lib/email/merge-tags.ts`): `{{first_name}}`, `{{email}}`, `{{job_title}}`, `{{company}}`, `{{client_name}}`, `{{owner_name}}`, a person's custom fields as `{{custom.<key>}}`, and a fallback after a bar (`{{company|your team}}`).
- **Audiences** (`src/lib/email/campaigns.ts`, `audienceWhere`): labels (any or all; the person's own or their organization's), excluded labels, owner, parent organization (everyone at it and at the organizations that are part of it), contacted or not contacted in N days, no campaign in N days, person custom fields (select, multi-select, checkbox), and client filters: category, pipeline, stage, Stripe product they're subscribed to now, client tag, churn reason and "open to coming back". An audience saved with the retired services filter still applies it, so it doesn't quietly widen, and the filters offer taking it off. A person matches a client filter when they're a matching client's contact or work at its organization. Filters are saved on the campaign or as a named audience (`audiences`, Email → Audiences) that campaigns reference; a campaign using one reads its filters when it sends and keeps a copy in case it's deleted. People without an email, archived, unsubscribed or whose address bounced are never included.

## Delivery tracking (Resend)

- Sends carry a `type` tag (`direct`, `campaign`). The Resend webhook (`/api/webhooks/resend`) receives `email.*` reports and `src/lib/email/delivery.ts` moves the matching `outbound_emails` row forward: sent → delayed → delivered → failed/suppressed → bounced → complained. One conditional `UPDATE` keeps a late or repeated report from moving it back. Opens and clicks are off by default (tracking pixels and rewritten links can hurt deliverability). A deployment turns them on with `email.trackOpens` / `email.trackClicks` in `app.config.ts` (or `NEXT_PUBLIC_APP_CONFIG`): the webhook then subscribes to `email.opened` / `email.clicked`, the first time and a count are stored on the row, and the timeline, campaign list and campaign report show them. Events for something that isn't tracked are ignored. Settings asks to reconnect the webhook whenever its events differ from what the deployment needs.
- A report that beats its row (the send is still saving) gets a 503 so Resend retries; a report for email another app sent on the same account matches nothing and is ignored, so it can never flag our people.
- A permanent bounce sets `people.email_bounced_at` (campaigns skip them; changing the address clears it). A spam complaint unsubscribes them. Both write a history entry on the person.
- Safety net: `/api/cron/email-status` runs hourly and asks Resend (`GET /emails/:id`) about emails with no final report after 20 minutes, for a week.
- Where it shows: a status badge on each sent email in the timeline, the delivery rate in the campaign list, and a report with every recipient on a sent campaign (plus opens and clicks when tracked).
- Settings → Email domains → Connect webhook subscribes to inbox and delivery events. A webhook connected before delivery tracking shows a notice to reconnect.

## Inbox (Resend)

- Domains and inboxes are managed through the Resend API from Settings → Email domains (admins). Resend stays the source of truth; nothing about a domain is stored here. `RESEND_DOMAINS` (optional) limits the CRM to some of the account's domains: `inEmailScope` in `src/lib/email.ts` filters `listInboxes`, the settings list and `syncThread` (so webhook events for other inboxes are ignored), and `assertDomainInScope` / `assertInboxInScope` guard every action that changes or sends from one.
- `src/lib/email/inbox.ts` mirrors threads into `inbox_threads` / `inbox_messages`. Each message becomes an `email` activity, so it shows on the timelines of the thread's person, organization and client. An email sent from a record (which already logged an activity) is matched by its Resend id and reused, so nothing shows twice.
- Links come from addresses: the first participant who is a person in the CRM, else an organization whose website matches the domain; the client is the one tied to that person or organization (current first). Teammates' own addresses are skipped while anyone else is on the thread. Linking a thread by hand sets `linked_by_hand`, and later syncs keep it.
- Mail into an inbox from a teammate's sign-in address (usually a thread they forwarded so it lands on a record) is credited to them (the activity's `user_id`, nothing else) once their domain's signature proves they sent it: the timeline reads "Sam forwarded an email", and it doesn't notify anyone as a contact's reply. The proof is forwarding's (`provenSender` in `src/lib/forwarding/inbound.ts`: the raw message from Resend, one From line, DKIM aligned with it or DMARC passing at a trusted receiver), since a From line alone can be forged. Mail that can't be proven stays mail that arrived, credited to nobody. Its own From and To are the teammate and the inbox, so the records come from the headers it quotes (Gmail's forwarded block, Outlook's From/To/Cc lines, "On …, Name <a@b> wrote:"; `src/lib/email/forwarded.ts`), and only from a proven message's (`provenForwards`): otherwise forged mail could pick the record it's filed on. A message is checked once, when it's first logged; later syncs read the answer from whether its activity was credited. Mail sent to the agent's forwarding address is different: the agent reads it and writes notes, as the sender ([AGENT.md](AGENT.md#email-forwarding)).
- Every email sent is credited to a teammate (the activity's `user_id`), shown as their initials in the conversation: one-off emails and inbox replies to whoever sent them, campaign emails to whoever created the campaign, labeled as a campaign and styled apart. Inbox replies and new emails record the sender in `inbox_sends` the moment Resend accepts them, and the sync credits the email from there whichever syncs it first: the send or Resend's webhook.
- Unread follows the record's owner, the same as text conversations (see [Unread](#unread-email-and-texts)). The thread's `read` flag is Resend's, kept in step both ways.

## Unread (email and texts)

Email threads and text conversations share one rule (`src/lib/conversations/read-rules.ts`, the SQL twin in `read-state.ts`):

- A conversation's unread belongs to whoever owns the record it's about: the linked person's owner, else (no person linked) the organization's. A deactivated owner counts as nobody.
- Owned: it's unread only for the owner, and only the owner opening it, or marking it read or unread, changes it. Everyone else still sees the conversation, not bold, with a line saying whose unread it is.
- Nobody's (no record, or no owner): it's unread for everyone, and the first teammate to open it marks it read for everyone.
- There's one `read` flag per conversation, not one per teammate, so when the record changes hands an unread conversation becomes the new owner's unread with nothing to copy.
- The sidebar's Email and Messages counts, the per-inbox counts and the Unread filters all count what's unread for the viewer. Email counts only the inbox folder from the last 90 days, as before.
- Open pages catch up on their own ([Live updates](#live-updates)); the Messages page also fetches what's new when the tab comes back into view, and push alerts cover the rest.
- Freshness: the Resend webhook (`/api/webhooks/resend`, signature-verified) syncs a thread as soon as mail arrives; a sync every 15 minutes (from the cron dispatcher) and the "Sync now" button catch anything missed. Syncing is idempotent.
- Received HTML goes through the same allow-list sanitizer as notes. The plain-text part is preferred when present, because sanitized marketing HTML reads poorly.

## Microsoft 365

Each teammate connects their own mailbox and calendar (Settings → Email and calendar, OAuth with PKCE, tokens encrypted with `src/lib/crypto.ts`). Email from records can go out through it (Graph, saved in their Sent Items); a quarter-hour cron syncs mail that has a person in the CRM from outside the organization on it (From, To or Cc), minus each teammate's block list, from Inbox and Sent Items or the folders they picked. Outlook's sensitivity label and a decision model (Jev, a yes/no probability) sort each one: on the record for the team, private to the teammate whose mailbox it came from (kept on `synced_emails`, never an activity), or not stored (marked with a category in Outlook); planned meetings assigned to them are kept in step on their calendar; and Calendar shows teammates' Outlook events live, as much as each shares. Email → My Outlook lists what was copied from the viewer's own mailbox, for them alone, like a mail client (deleting an email there can block its sender), and Email → Block list edits their block list; owners can see who's connected and disconnect a teammate (Settings), never read their mail. See [MICROSOFT.md](MICROSOFT.md).

## Calling and texting

Twilio numbers, managed in Settings → Phone numbers. Calls are placed from the browser with the Twilio Voice SDK through a TwiML app whose webhook only dials calls the teammate prepared; incoming calls are forwarded to a cell phone, logged on the caller, and leave a write-up task. Texts both ways are activities, and every text joins a conversation on the Messages page; STOP opts a person out. Text campaigns share the email campaigns' audiences and claim-and-resume sending. Every Twilio webhook is signature-checked and idempotent. See [PHONE.md](PHONE.md).

## The agent

Record pages open with an AI summary of the record, shared by the team and rewritten once a day. A chat panel in the bottom right corner that reads and changes records as the signed-in teammate, with their role, through the same operations as MCP. Threads are saved per teammate; it can talk (speech to speech) and take dictation. Longer jobs (web research, adding an organization's people, cleanups across a list) run in the background on an eve agent in `agent/`, started from chat, by mentioning the agent in a note, by assigning it a task or by a scheduled job. Teammates attach spreadsheets, Word documents and text files in chat (read in the browser; only the text is sent), and save skills and scheduled jobs for it in Settings → Agent, where admins share some with the whole team. A run acts as the teammate who asked, through the same MCP tools and role checks, and its changes read "Sam via Agent". It never sends email or texts: it writes drafts the teammate reviews and sends. The team can also forward email to the agent's address (or Cc it on a thread): the agent records what matters on the right records, as whoever sent it, and the CRM emails its answer back to them, so a back-and-forth works by reply ([AGENT.md](AGENT.md#email-forwarding)). Everything runs through Vercel AI Gateway. See [AGENT.md](AGENT.md).

## Phone app and notifications

- **Installable.** `src/app/manifest.ts` and the generated icons (`icon.tsx`, `apple-icon.tsx`, from `app.config.ts`'s `pwa` settings and brand color) make the CRM installable from the browser: Add to Home Screen on iPhone and iPad, Install app on Android and desktop. It opens full screen and respects the notch (`viewport-fit=cover`, safe-area padding in the shell and the agent). The proxy lets the manifest, icons and service worker through without a session, since phones fetch them before anyone signs in. On a phone's browser the sign-in page shows a card at the bottom with how to install (`src/components/pwa/install-prompt.tsx`: Android's own install dialog when the browser offers one, the Share → Add to Home Screen steps on iPhone). Opened from the Home Screen, the app asks once to turn on notifications for that phone (`notifications-prompt.tsx`, with a button, since iPhones only show the permission dialog after a tap). Either card, once closed, stays closed in that browser for a while.
- **On a phone** (under the `lg` breakpoint) the sidebar becomes a tab bar (Home, Clients, Activities, Team chat, More; People and the rest are under More) and a top bar with New, Search, the agent and, on a record page, a back button that returns to the list as it was. The shell publishes its size as `--shell-top` and `--shell-bottom` (zero on a desktop): full-height pages use `h-app`, `main` clips sideways overflow so one wide element can't make the page wider than the screen, and sticky or floating things offset by them so nothing hides under the bars. While a text field has focus on a touch screen the tab bar steps aside for the keyboard. Tables become lists (a column's `mobile` option picks what shows under each row's title), toolbars scroll sideways, dialogs and search open as sheets, and touch screens get 16px text fields (so iOS doesn't zoom) and larger targets through `pointer-coarse:`.
- **The service worker** (`public/sw.js`, always served fresh) shows notifications and, when one is tapped, focuses an open CRM window and navigates it, or opens one. It doesn't cache pages: everything is behind a login and changes constantly.
- **Push** is Web Push with VAPID keys (`src/lib/push/vapid.ts`; locally a pair is made in `.data/vapid.json`, deployed it needs `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`). Settings → Notifications turns it on per device and picks that device's alerts. iPhones and iPads need the app installed to the Home Screen first; the page says so.
- **What notifies** (`src/lib/push/triggers.ts`, called from the service layer, so the browser, API, MCP and the agent all notify the same way, and nobody hears about their own change). Each device picks its own:

  | Push alert | When |
  | --- | --- |
  | Tasks assigned to me | Someone else creates or reassigns a task, or a planned call or meeting, to you |
  | Tasks with a time | On the day, 15 minutes before a task or planned call with a time is due |
  | Today's tasks, in the morning | One summary of today's tasks with no time, from `notifications.morningHour` (7 AM) workspace time |
  | Meetings | 15 minutes before each of your meetings |
  | Mentioned in a note | A teammate mentions you in a note or a reply (an email goes out too, see Mention emails below) |
  | Replies to my notes | Someone replies to a note you wrote or already replied to |
  | Mentioned in team chat | A teammate mentions you in the team chat (an email goes out too) |
  | Every team chat message | Anyone posts in the team chat. Off on new devices |
  | Records assigned to me | Someone else makes you the owner of a client, person or organization |
  | Notes and activity on my records | Someone else adds a note, reply, call, email, text, meeting or task on a client, person or organization you own, through the app, the API, MCP or the agent (`logActivity`, `replyToNote`). Synced mail, texts and calls don't count: they have their own alerts |
  | Stage changes on my clients | Someone else moves a client you own to another stage, or signs, loses or wins it back |
  | Replies from my contacts | Mail arrives in a connected inbox from a record you own (received in the last day, so a first sync doesn't flood you) |
  | Texts from my contacts | Someone you own texts one of the team's numbers, or a number you look after |
  | The agent finished | Background work you gave the agent is done, has a draft for you, or couldn't finish |

  One event sends each device one alert: the first it wants, most specific first (`notifyEach` in `src/lib/push/notify.ts`, the order in `src/lib/push/routing.ts`). A note on your client that mentions you is "mentioned you" on a device that wants mentions, else "added a note on Acme" on one that wants activity on your records. A new device gets every alert but every team chat message (`defaultNotificationKinds`).

  The scheduled ones run on the quarter-hour notifications cron (`src/lib/push/due.ts`, rules in `src/lib/notifications/schedule.ts`), so a reminder lands 0–15 minutes before its time: exactly 15 for meetings on the quarter hour.
- **Mention emails** (`src/lib/notifications/mentions.ts`, template `src/emails/mention.tsx`): when a teammate is mentioned in a note or a reply on a client, person or organization (or a note on no record), or in the team chat, they also get an email: who mentioned them and where, what was written (up to 2,000 characters), a button to the note (`/clients/<id>#a-<note id>`, which the timeline scrolls to) or the message (`/chat#m-<id>`), and a link to the record. On unless the teammate turns it off in Settings → Notifications → Mention emails (`users.prefs.emailMentions`, `note` and `chat`); push alerts for the same mentions stay per device. Sent after the response, from whatever made the change (the browser, the API, MCP or the agent), never to the writer, to deactivated teammates or to ones who never signed in. Each is claimed in `notifications` (kind `note_mention_email` or `chat_mention_email`, dedupe key per note, reply or message) before it goes out, and released if the send fails. An edit to a chat message emails only the teammates it newly mentions; editing a note doesn't send anything.
- **Agenda emails** (`src/lib/notifications/agenda.ts`, template `src/emails/agenda.tsx`), chosen per teammate (`users.prefs.emailDigests`), off until turned on:
  - **Daily**, every weekday morning: today's meetings, tasks due today and anything overdue.
  - **Weekly**, every Monday morning: this week's meetings, tasks due today or overdue, and tasks coming up later in the week. On a Monday with both on, only the weekly one goes out.
  - Sent from `notifications.morningHour` in the workspace's time zone by the same cron, once per teammate per day (claimed in `notifications` before sending, released if the send fails), and skipped when there's nothing on the agenda. Settings → Notifications can send a preview.
- **Sending** happens after the response (`after()`), so a slow push service never slows the change. Each notification is a row in `notifications` with a dedupe key, so a retried webhook or overlapping crons send it once. A device the push service reports gone (404/410) is deleted; one that fails 5 times in a row is dropped.

## Background jobs

Three Vercel Cron entries (`vercel.json`), on the same quarter-hour blocks so the database can scale to zero between them (Neon suspends after a few idle minutes):

- **The dispatcher** (`/api/cron/tick`, `src/lib/cron-tick.ts`), at :00, :15, :30 and :45. One statement asks what's due (`whatIsDue`), then it runs only the jobs that have work, each on its own so one failing doesn't stop the rest, and stops starting new ones after four minutes (they go next time). A quarter hour with nothing to do is one query and no writes. The jobs: meeting and task pushes and the morning summary (when one is due, or in the morning window), agenda emails (in the morning window, when someone wants them), email and text campaigns (scheduled or interrupted ones), the agent's scheduled jobs and the safety net for background runs, forwarding replies that didn't go out, describing files nobody has described yet, the inbox sync (every quarter hour, writing only what changed: Resend's webhook delivers mail as it arrives, this catches anything it missed), the Microsoft 365 mailbox sync (on the blocks that fit `microsoft.syncEveryMinutes`) and the daily prune (09:00 UTC).
- **The delivery check** (`/api/cron/email-status`), hourly at :00.
- **The Stripe sync** (`/api/cron/stripe`), once a day at 09:00 UTC: customers, subscriptions, invoices and payments.

Each job's own route (`/api/cron/campaigns`, `agent`, `inbox`, `notifications`, `microsoft`) still works when called by hand with the cron secret. **The daily prune** (`src/lib/daily-prune.ts`) deletes notifications older than 90 days (they only stop a push or email going out twice), expired invite and reset links, expired sessions and rate-limit counters from windows that ended two days ago, clears forwarded emails' text after 30 days (and drops them after 180), and clears the request and answer text of finished background runs 90 days after they left the agent panel, keeping the run and its cost. History (`events`) is never pruned. Nothing runs more often than every 15 minutes. The browser's only repeated request is the live-update check below, which stops when no one is using the page. Scheduled campaigns are rounded up to the next quarter hour, so they go out exactly when the cron runs. Work someone starts by hand ("Send now", "Sync now") runs right away.

## Live updates

Open pages show changes without a reload: a task the agent just added, a call that came in, a teammate's edit.

- **How:** `LiveUpdates` (`src/components/live-updates.tsx`, in the `(app)` layout) asks `/api/live` for the newest change in three scopes (`src/lib/live.ts`, one statement with the session check, each an index lookup): `records` (the latest `events.created_at` or `activities.updated_at`), `chat` (`chat_messages.updated_at`) and `mail` (`inbox_threads.updated_at`, `text_threads.updated_at`). Each page shows some of them (`pageScopes` in `src/lib/live-rules.ts`: `records` almost everywhere, `mail` on the inbox and Messages, nothing on the team chat). When a scope the page shows moved, `router.refresh()` re-renders the page and the sidebar counts on the server; when only another one moved (a chat message while on a client), just the sidebar's badges are fetched (`/api/live/badges`, one statement) and nothing else re-renders. What's typed, open or scrolled in the browser stays as it was.
- **Your own change refreshes once.** The layout reads the versions on every render, alongside the session check, and hands them to `LiveUpdates`, which takes them as seen. The render a server action's `refresh()` triggers therefore also brings the versions that include that change, and the next check doesn't refresh again for it. A page load starts from them too, so it doesn't ask `/api/live` on its own.
- **The team chat follows along itself.** The chat page is rendered with the chat's version (read with its messages); when `chat` moves it fetches only what was posted, edited or deleted since (`chatChangesSince`) and merges it in. Posting, editing, deleting and marking the chat read don't re-render the page: marking read returns the badges.
- **What changed glows.** While a refresh lands, `watchArrivals` (`src/components/live-highlight.ts`) watches the page's content and gives whatever appears or changes (a new task or note, a field's new value, a count) a short glow, so the agent's work is seen happening on the page that's open. It never navigates: a change to a record that isn't on screen shows when the teammate goes there. What the teammate is typing in, and a refresh that swaps most of the page, glow nothing. Mark an element `data-live-quiet` to leave it out.
- **When it asks:** right away after each agent tool call (chat and voice, `checkForChanges()`), while one of the teammate's background tasks is going (the task list returns the versions with it, every 4 seconds in a task's first minute and every 12 after, so no separate check), when the tab comes back into view or the window regains focus, and every `live.pollSeconds` (30) while the tab is visible and someone clicked or typed in the last `live.idleMinutes` (2). The team chat page asks every `live.chatPollSeconds` (5) instead, under the same idle rule, so messages show up within seconds. Hidden or idle tabs don't ask, so a CRM left open overnight lets Neon suspend.
- **Cost:** a check is one small function call and one indexed query. A dozen people working 8 hours a day is about 250,000 checks a month, well within Vercel Pro's included invocations, and the database is awake during working hours anyway. Raise `live.pollSeconds` to ask less often, or set it to `0` to rely on focus and agent checks alone.
- **Why not sockets:** a push service (Pusher, Ably) or Neon's logical replication would add a vendor or keep the database from sleeping, for a difference of a few seconds. `activities.updated_at`, set by Drizzle on every update (`$onUpdate` in `schema.ts`), keeps the check honest for edits that don't set it by hand.

## Stripe

Stripe is the source of truth for billing. The CRM reads it, and admins can make a few changes to subscriptions from a client's page (below); the CRM keeps no billing of its own.

- **Accounts.** Each `STRIPE_SECRET_KEY_<NAME>` in the environment is one Stripe account (`src/lib/stripe/accounts.ts`), with `STRIPE_ACCOUNT_LABEL_<NAME>` as what the app calls it; plain `STRIPE_SECRET_KEY` is the account called `default`. Restricted, read-only keys are enough to see billing; changing subscriptions needs write access to Subscriptions too. `src/lib/stripe/index.ts` is the REST client (no SDK).
- **A daily copy.** `/api/cron/stripe` (`syncStripe` in `src/lib/stripe/sync.ts`) lists every customer, subscription and product in each account into `stripe_customers` and `stripe_subscriptions`: a few dozen requests a day however many clients there are, where a lookup per email would be thousands. What a run didn't see was deleted in Stripe and is removed. An account that fails keeps its last copy.
- **Matching is by email, and computed, not stored.** A Stripe customer belongs to a client when its email is one of the client's people's: its contact, the people added to it, and everyone at its organization, other emails included (`clientCustomers`). Nobody sets a customer ID. Adding a person or an email changes the match with nothing to re-link. `client_stripe_links` holds only the exceptions: a customer linked by hand (its billing email isn't on anyone), and a match marked as not theirs.
- **Flags on the client.** After each sync, `refreshClientBilling` rolls a client's matched subscriptions up into `clients.stripe_status` (worst news first: a payment problem outranks a healthy subscription; rules in `src/lib/stripe/rules.ts`), `stripe_mrr` (normalized to a month, after discounts), `stripe_discount` (what discounts take off a month), `stripe_collected` (what they actually paid in the last 365 days, less refunds), `stripe_owed` (left on open invoices), `stripe_credit` (credit on their customers) and `stripe_products` (names of the products they're subscribed to). The Clients table shows the status ("No subscription" when nothing is billing them) and the products, as its Stripe and Services columns, filters on them and sorts by status, and the API returns them as `billing`. Both columns show only when Stripe is connected. A status change is written to the client's history as `billing_changed`, except the first time a client is seen.
- **Discounts come from what was billed, collected from what was paid.** A subscription's discount is read off its latest invoice (discounts as a share of the subtotal, `discountShare`), so every kind of coupon is covered without working each out; `stripe_subscriptions.net` is the list amount less that share. Collected is added up from a year of payments (`chargesSince`): what was captured, less refunds, per customer, for the last 30 and 365 days. Money paid outside Stripe (a check marked paid by hand) isn't in it. Usage-based prices have no fixed amount and count as zero.
- **The client page reads live.** The billing card (every category, prospects included) reads each matched customer's subscriptions, invoices, payments and saved cards from Stripe, keeping each customer's answer for two minutes (`cachedBillingFor`; "Check Stripe now" always reads live), in its own `<Suspense>` boundary so a slow Stripe never holds up the page. The card is the highlights; "See details" opens each customer in full. A client the daily sync hasn't reached in 26 hours is looked up by email first (`syncClient`), which is also what "Check Stripe now" does.
- **The card.** Subscriptions (monthly, after discounts), overdue invoices (what's left on invoices past their due date) and what was collected in the last 12 months ("Collected LTM") sit in one row, then the running subscriptions. The details merge every matched customer: who each is (and opening or removing them), then collected (LTM and 30 days), balance, open and overdue invoices across them; each subscription as a card, with its next charge; saved cards and bank accounts drawn as cards, each customer's default first; and invoices and payments in one table, newest first, each labeled and with its own status (an invoice is paid, unpaid, overdue or void; a payment succeeded, failed, pending or refunded). An invoice says what it was for, from its lines: the products by name (`invoiceItems` in `src/lib/stripe/rules.ts`, reading either API version's line shape), or a one-off line's description, with its number under it; a payment for an invoice says the same. With several customers, each subscription, card and row names the customer's billing email, and a switch at the top (All, or one customer) narrows everything to one. A switch above the table shows all of it, only invoices or only payments.
- **Next charges are inferred.** `nextCharge` (`src/lib/stripe/rules.ts`) works out when each subscription bills next and roughly how much from what Stripe already returned: the end of its period (or trial), its fixed price lines at the discount its latest invoice had. Nothing is billed next for one that's paused, ended, unpaid or set to cancel by then; usage-based lines are left out and said to be. It isn't Stripe's upcoming invoice (no extra request, and no tax, proration or credits), so the details call it scheduled and say it's an estimate. Each subscription's next charge sits at the top of the invoices and payments table, soonest first; it shows under Invoices, and under Payments too when the subscription charges automatically.
- **The Billing page** (`/billing`, in the sidebar between Files and Team chat when Stripe is connected) lists every invoice and payment in one table (`stripe_activity`, queries in `src/lib/stripe/billing-page.ts`, rules in `src/lib/stripe/activity.ts`): customer, the clients it belongs to, type, date, status (paid, unpaid, overdue, failed, refunded, void…), amount and links to the invoice, PDF or receipt. Every column but the links sorts, and it filters by search (customer, client, invoice number, description), type, status, mapping, Stripe account and date range, all in the URL; rows load as it's scrolled. Totals above it (collected, invoiced, outstanding, not mapped) follow the filters, per currency. A row whose customer no client has is tinted with a warning edge and a "Not mapped" badge, with Map beside it. The sync copies invoices (drafts left out) and payments with the customers: the last 365 days each run, which catches anything paid, refunded or voided lately, and all of history the first time; older rows are kept and rows in the window that Stripe no longer lists are removed. An open invoice older than the window that Stripe no longer lists as open is read again, so one paid or voided since doesn't stay unpaid. A payment only authorized so far is pending and counts as nothing collected; one captured for less counts what was captured. Looking a client up (`syncClient`) saves its payments and open invoices too, once the daily sync has copied the account's history (before that, they'd make the first run skip it). Admins can run the sync from the page ("Sync now").
- **Mapping customers to clients.** The Billing page's "Customer mapping" tab lists the Stripe customers with the clients each belongs to, whether by email or by hand, how much activity it has, what it paid in the last year and when it last had activity; it opens on the ones no client has, with their count on the tab. "Map to client" picks a client and links the customer by hand (`linkStripeCustomer`, the same link a client's billing card makes, recorded as `stripe_linked`), so a customer billed through an address nobody at the client has (a shared billing inbox, an accountant) counts on the client from then on. The × on a client takes the customer off it (`removeStripeCustomer`): a link made by hand is undone, and an email match is marked as not theirs. A customer only archived clients have shows as not mapped; a payment taken without a customer can't be mapped and isn't counted as not mapped.
- **Admins change subscriptions in Stripe.** From the details an admin can start a subscription (a plan, or a different amount on the same product and period, charged to a saved method or invoiced, with an optional trial), change one (plan, amount, quantity, how it's paid, and how the change is prorated), cancel one at the end of the period or immediately, and take back a cancellation that hasn't happened yet. The dialogs say in a sentence what will happen before anything is sent; a subscription set to cancel shows "Cancels Dec 15" everywhere until it does. The actions (`src/actions/billing.ts`, request forms in `src/lib/stripe/changes.ts`) check the customer belongs to the client, send an idempotency key so a double click can't start two subscriptions, write `stripe_subscription_created`, `_changed`, `_canceled` or `_kept` to the client's history, and read the client back from Stripe so the card and the Clients table update at once. They aren't API operations or MCP tools: the agent never changes billing.

## Local fallbacks

Every external service is optional in development (see the README). The fallbacks refuse to run on Vercel, so production can't silently use them.
